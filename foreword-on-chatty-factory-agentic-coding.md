\##What this is##



This factory is designed to achieve positive outcomes of working outputs from a non-coder request. Plain language in, a working project or addition to a project one patch at a time. It is not a magic "ask it to make something and expect it to hit the mark 100% of the time" and anyone claiming their project is that is stretching the truth. Even frontier cloud models cannot achieve this. Chatty-factory is designed to achieve success some of the time, it may require you to attempt a build or patch several times before getting the desired outcome, but the point of it is to get the desired outcome eventually, not every time.



It is our hope that over time the negative constraints library will help the factory achieve a better success rate over time the more it is used, especially if community curation occurs. Multiple people sharing their own libraries, even potentially creating model specific libraries over time. This should result in acting like bumper lanes funnelling the ai away from bad choices and towards good choices for how to achieve a build or patch.



As a secondary bonus, this could create a situation where aggregate data for specific models could potentially outline exactly how good specific models are for specific tasks, negating much of the "plug it in and pray it can do the assigned task" and leading to a situation where it becomes clearer that the model you are building with genuinely does not have the ability to build or patch your request, requiring a different llm to be used inside chatty-factory.



\##What this is not##



As stated before, chatty-factory is not a one and done, send it and ye shall receive magic box of coding wonder and delights. It is a negative constraints led factory able to achieve small, bounded projects that consist of outputting a foundational, working project and then patching to complexity one moving part at a time. It is not able to do any task, it is restricted to the llm pilot's reasoning and native dataset boundaries. It is not expected to succeed straight out of the box the moment you install and fire it up and ask for a project, it should be viewed as any learning student would be - it will make mistakes at first, potentially many mistakes, but over time it will learn to make less mistakes as you request work and it's library begins filling in, reducing the possible "won't work" options for it to take.



It is not designed as a cloud replacement, it is designed as a hybrid option. Some projects will require reasoning and edge case, up to the moment data that small, local models simply do not have currently. It should be seen as complementary; use cloud when you need it, use chatty-factory for the mundane tasks where cloud would be overkill. Eventually an optional api key lane will be added to make this hybrid flow more viable and easy to implement (likely v0.3).
